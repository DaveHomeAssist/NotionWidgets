## What This App Actually Is

NotionWidgets is a small collection of four embeddable HTML widgets designed to drop into Notion embed blocks. Three of them (Client Approval, Quest Log, Project Status) are compact, self-contained single-file widgets configured entirely by URL parameters. The fourth (Workspace Topology Map) is a full interactive D3-powered graph explorer that fetches JSON datasets from a `maps/` directory.

There is also a landing page (`index.html`) that acts as a catalog of the widgets with live links and example URLs.

What it does well: each widget actually works. The visual design is polished. The URL-parameter contract is well-documented and well-validated. The three smaller widgets are genuinely self-contained (no external dependencies). Input handling and sanitization are materially above average for a personal project.

What it does not do: these widgets have no persistence. The Client Approval widget fires a `postMessage` but nothing receives it unless a parent iframe is listening. The Quest Log and Project Status are display-only — there is no way to update data from within the widget. This is by design, but it means the "interactive" label on the approval widget is partly aspirational unless you have a receiving integration.

## Main User Goal

There are two user personas:

1. **Dave (the builder):** Wants to embed polished micro-widgets into his Notion workspace to make pages look better. He configures them via URL params, pastes embed URLs, and moves on. The flow works for this.

2. **Hypothetical buyer/user:** Someone who finds these widgets and wants to use them in their own Notion workspace. They need to: (a) understand what each widget does, (b) figure out the URL params, (c) construct a valid URL, and (d) embed it. Steps (a) and (d) are easy. Steps (b) and (c) are painful — there is no configurator UI, and constructing JSON-encoded URL params by hand is hostile to non-technical users.

The gap between "this exists" and "someone can actually use it" is the biggest strategic problem in the project.

## Architecture Assessment

### What's Good

- **Single-file widget contract is clean.** Three of four widgets are truly self-contained — one HTML file, zero external dependencies. This is rare and genuinely valuable for the Notion embed use case.
- **URL-parameter API is well-designed.** JSON array params for structured data, token allowlists with fallbacks, legacy format support with deprecation warnings. The validation in `client-approval.html` (type/status aliases, normalization functions) is notably thorough.
- **Safe DOM rendering in the three smaller widgets.** `createElement` + `textContent` pattern is used consistently. No innerHTML in the approval, quest, or status widgets.
- **Schema validation for the graph explorer.** `validateDataset()` checks node uniqueness, edge references, orphan detection, and schema versioning. This is better than most professional tools manage.
- **Graceful degradation on bad params.** Invalid JSON falls back to defaults. Invalid tokens normalize to safe values. Malformed numbers get clamped. The widgets do not crash on bad input.
- **Light/dark mode on all surfaces.** Every widget responds to `prefers-color-scheme`. The workspace map adds a manual toggle with localStorage persistence and URL param override.
- **URL state sync on the workspace map.** Selected node, filter state, heatmap, path mode, and theme all roundtrip through the URL. Bookmarkable deep links work.

### What's Wrong

- **The workspace map is a completely different kind of application than the other three widgets.** It loads external libraries, fetches JSON at runtime, uses innerHTML heavily, and requires 1,442 lines of tightly coupled rendering logic. It does not share the architectural qualities that make the other three widgets good. Treating it as "just another widget" in the same repo creates confusion about what the project's rules actually mean.
- **No shared CSS or JS patterns.** Every widget re-implements its own design tokens, its own `clampNumber()`, its own `parseJsonArrayParam()`. The `engine/validate.js` module exists but is not used by the thing that needs it. There is no mechanism to share code without violating the single-file rule.
- **The single-file rule forces harmful duplication.** Each widget carries 40-60 lines of identical helper code. When `clampNumber()` gets a bug fix in one widget, it needs to be manually mirrored to the others. The project is small enough that this has not broken yet, but the issue tracker already has 6 open items, and fixing any of them requires touching multiple files identically.
- **No test infrastructure at all.** Zero tests. No way to verify that URL param contracts still work after changes. No visual regression checks. No validation that example URLs on the landing page produce expected output.

## Visual Design

### Strengths

- **Consistent dark-mode aesthetic.** All widgets share a similar look — dark surfaces, subtle glow effects, monospace accents, rounded cards. Even though the CSS variables differ, the visual output is cohesive.
- **Effective use of color for status communication.** Green/approve, yellow/warning, red/danger is used consistently across widgets. The color-coded top borders on landing page widget cards are a nice touch.
- **Typography hierarchy is clear.** The combination of system-ui sans-serif for body text and monospace for labels/badges creates good visual separation between data and metadata.
- **Animations are tasteful when they work.** The ring chart fill, XP bar progression, and staggered phase reveals all feel polished and purposeful — they communicate progress, not just decoration.
- **The workspace map is genuinely impressive.** Pan/zoom, node focus, heatmap overlay, path finding, detail panel — this is a real data visualization tool. The layout, color coding, and interaction design are significantly above "side project" quality.

### Weaknesses

- **The landing page hero section breaks on narrow viewports.** The grid `grid-template-columns: minmax(0, 1.3fr) minmax(280px, 0.9fr)` at line 81 forces a two-column layout until 960px. Between 600-960px, the right column stat cards compete with the hero copy for limited space.
- **Widget cards on the landing page show raw URLs.** The "Example" URL blocks display 300-400 character percent-encoded strings. These are intimidating, not informative. A non-technical user sees `%5B%7B%22name%22%3A%22Homepage%20mockup%22` and closes the tab.
- **No empty states on the three smaller widgets.** If all URL params are omitted, each widget renders hardcoded sample data. This is reasonable for demo purposes, but there is no visual indicator that the user is seeing defaults vs. their actual configuration.
- **Success overlay in Client Approval uses a hard black background.** Line 391: `rgba(0,0,0,0.85)` overlay works in dark mode but in light mode it creates a jarring contrast shift.
- **Text contrast in light mode is untested.** Light mode variables are defined but several `--text-dim` values (e.g., `#8a8aa4` on the landing page, `#8888a0` in project-status) may fail WCAG AA 4.5:1 contrast against their respective surface backgrounds.

## Accessibility

| Area | Status | Notes |
|------|--------|-------|
| **Semantic HTML** | Partial | Landing page uses `<section>`, `<article>`, `<h1>`-`<h3>`. Widget pages use generic `<div>` for everything except the workspace map which has `<main>`, `<header>`, `<aside>`. |
| **Keyboard navigation** | Poor | Landing page links are keyboard accessible. Widget buttons in client-approval are focusable. Workspace map nodes have `tabindex` and keyboard Enter/Space handling. But quest-log and project-status have zero interactive elements and no skip links. |
| **Screen reader support** | Poor | No `aria-pressed` on approval buttons. No `aria-live` regions for error/success states. No `role="alert"` on the error bar. Quest log and project status have no ARIA landmarks at all. Workspace map has an `aria-live` announce div (line 320) and node `aria-label`s — this is the best of the four. |
| **Focus management** | Poor | After approval submission, focus is not moved to the success overlay. After error display, `feedbackArea.focus()` is called (line 737) which is good, but the error bar itself is not announced. |
| **Reduced motion** | Partial | Workspace map has `prefers-reduced-motion: reduce` (line 311-316). The other three widgets do not. |
| **Color contrast** | Unknown | Light mode `--text-dim` values need testing. Dark mode appears adequate by inspection but has not been measured. |
| **Focus indicators** | Good | Landing page defines `:focus-visible` with a gold outline (lines 65-72). Workspace map nodes show focus via border change. Client Approval textarea shows focus ring. |
| **Alt text / labels** | Mixed | Workspace map SVG has `role="img" aria-label`. Favicon images are decorative (acceptable). No alt text documentation for emoji icons used as functional indicators. |

## The One Thing That Matters Most

**Fix S1-1: The workspace map violates the project's own core rule.**

The README says "No external JavaScript, external CSS, CDN assets, or Google Fonts in shipped surfaces." The workspace map loads Google Fonts, D3, and Dagre from CDN. This is not a minor inconsistency — it is the foundational product rule. If the rule is wrong, update it honestly. If the rule is right, the map needs to either inline its dependencies or be clearly separated as a different kind of surface with different rules.

Every other issue in this audit is secondary to the question of whether this project's stated contract is actually true. Right now, it is not.
